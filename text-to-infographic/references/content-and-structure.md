# 从文本到结构

这是唯一需要判断力的环节。后面全是机械执行。

---

## 1. 压缩到 3–7 个信息单元

读一遍原文，边读边提取：主题与一句话结论、关键事实、关键数字（含单位与口径）、
实体、时间点、因果、行动项、风险与前提。

然后按顺序裁剪：

1. 合并语义重复项
2. 「观点 + 解释」合成一个单元，解释进 `body`
3. 删掉不能支撑 `core_message` 的背景
4. 保留关键数字与差异点（差异比绝对值更有信息量）
5. 优先保留带明确关系的单元——无关系的单元最后一定沦为孤立卡片
6. 收敛到 3–7 个主单元
7. 次要信息降级为 `body`、页脚 `note` 或下一页，**不静默丢弃**

忠实度优先于视觉：原文明确写出的限制条件，即使不好画也要留在页脚。

### 标题写结论，不写主题

`title` 是整张图被读得最多的文本。

| 不推荐（主题标签） | 推荐（结论短语） |
|---|---|
| 成本问题 | 部署成本集中在人工复核 |
| 试点情况 | 三个试点均在第 6 周回本 |
| 技术方案 | 零依赖后端换取可控的审计面 |

≤ 24 字。写不出结论短语，通常说明这个单元语义还没切清楚，回到切分重做。

### 常见失败

| 症状 | 根因 | 修正 |
|---|---|---|
| 7 个单元都像并列要点 | 没识别单元间关系 | 补 `precedes` / `contains` / `contrasts_with` |
| 单元大量重复 | 切分过细 | 按语义合并，细节降级为 `body` |
| 关键数字消失 | 把数字当细节删了 | 数字进 `value` 或页脚 |
| 单元无法独立理解 | 缺上下文 | 补 body，让单元自足 |
| 全部单元同等重要 | 没做权重区分 | 只给 1–2 个单元 `emphasis: high` |

## 2. 选结构：看关系，不看关键词

出现「相比」不等于对比图，出现日期不等于时间线。

### 五类模式的成立条件

`comparison` 对比 —— 必须同时满足：≥2 个并列实体；≥2 个**共享**评价维度；
阅读目标是识别差异或做选择。单边罗列优点不是对比。

`process` 步骤 —— 必须同时满足：关系以 `precedes` / `depends_on` 为主；
有明确起点和终点；顺序不可随意交换。

`hierarchy` 层级 —— 必须满足：`contains` / `belongs_to` / `specializes` 占主导；
存在明确父子或整体-部分关系。**反例：三个并列要点不是层级**，强行画树属于结构造假。

`funnel` 漏斗 —— 必须同时满足：同一批对象被逐层筛选；阶段之间存在数量、比例或范围的
**真实收缩**。只有五个步骤而没有收缩含义时，用 `process`。

`timeline` 时间线 —— 必须同时满足：≥3 个时间节点；时间顺序是理解内容的主轴。
日期只是附加属性时不成立。

`overview` 兜底 —— 结构置信度低、或内容确实只是「一个观点 + 若干支撑」时用。

### 选定后说一句为什么否决次优

不需要打分表，但要在心里（和交付说明里）能回答：

> 次优模式是 X，落选原因是什么？

例如「时间线落选：日期仅为阶段标记，交换两段顺序后语义仍成立」。
这一步能挡住绝大多数「看到日期就画时间线」。

## 3. 版式矩阵

渲染器实际支持的 `pattern:layout`（写错则回落到该 pattern 的默认版式）：

| pattern | layout | 适用 |
|---|---|---|
| `process` | `horizontal-steps` | 3–5 步，横版默认 |
| `process` | `vertical-roadmap` | 步骤多或竖版画布 |
| `process` | `cycle` | 循环闭环 |
| `comparison` | `split-2` | 两个实体，共享维度 |
| `comparison` | `matrix-3` | 三个及以上实体 |
| `comparison` | `before-after` | 前后状态，中部箭头 |
| `comparison` | `pros-cons` | 优势 / 风险两栏，靠 `items` 填充 |
| `hierarchy` | `top-down-tree` | 父子树，正交折线连接 |
| `hierarchy` | `radial-tree` | 单根多分支，径向布局 |
| `hierarchy` | `layered-pyramid` | 抽象层级，越往下越具体 |
| `funnel` | `centered-funnel` | 经典居中收缩漏斗 |
| `funnel` | `horizontal-conversion` | 横向递减条，带数值 |
| `funnel` | `narrowing-pipeline` | 左→右管道收缩 |
| `timeline` | `horizontal` | 卡片同侧，日期在轴下 |
| `timeline` | `alternating` | 卡片上下交替 |
| `timeline` | `vertical` | 竖版画布或事件较多 |
| `overview` | `radial-hub` | 中心辐射，兜底 |

省略 `layout` 时的自动选择：comparison ≤2 实体 → `split-2` 否则 `matrix-3`；
process 竖版且节点 >3 → `vertical-roadmap` 否则 `horizontal-steps`；
timeline 竖版 → `vertical` 否则 `horizontal`；其余取表中首个。

**内置版式不够用时**，用 `--layout-file` 注入自定义版式（见 `ir-and-renderer.md` §5），
不要为了塞进模板而砍内容。

## 4. 防卡片堆砌

渲染后逐条自检：

1. 一页只有一个主要叙事方向
2. 至少 70% 的节点通过连线、位置或容器体现关系
3. 不允许所有节点同权重
4. 有明确的视觉入口，也有收束点
5. 标题是结论不是标签

**交换测试**（最关键）：任意交换两个信息块的位置，若页面含义几乎不变，
那它就是卡片网格。此时回到关系建模，不要调配色和间距。

---

## 5. 分页

按语义章节分页，不按字数分页。推荐页面角色序列：

| 页 | 角色 | 承担的问题 |
|---|---|---|
| 1 | overview | 问题是什么 |
| 2 | explanation | 为什么会发生 |
| 3 | solution | 应该怎么做 |
| 4 | 证据 | 凭什么这么说 |
| 5 | 行动 | 接下来做什么 |

出现任一情况即应分页：主单元 > 7；同时存在两个强关系模型；正文在合理字号下装不下；
大量关键数字需要保留；内容同时包含背景—分析—建议；单页需要超过两层视觉层级。

多页不是互不相干的海报集合：每页要能回答「它在整体论证里承担什么」，
可用页脚 `note` 承接上一页结论。

### 比例

| 场景 | 比例 |
|---|---|
| 屏幕演示、嵌入文档 | `16:9`（默认） |
| 打印、PDF | `4:3` |
| 社交平台方图 | `1:1` |
| 手机长图、竖屏 | `9:16` |

竖版画布下渲染器会自动把 process / timeline 切成纵向版式。
